■ 6. 決定事項と、その理由
================================================================================

  D1. 当面は単一HTMLのまま進める。React Flow への移行はまだしない。
      理由：ビルド不要ですぐ試せるのが実験段階では最速。
      移行の判断は、機能がある程度出揃ってから行う。
      ※ ユーザーからは「HTML1つで実装が辛ければ、Reactとかで
        ファイル分割してもよい」との許可が出ている。辛くなったら提案すること。

  D2. UIコードは書き直しが効くが、データの形は書き直しが効かない。
      よって新しい概念を持ち込む機能は、実装前に必ずデータの形を
      ユーザーと相談して決めること。これは実際に (6)(7) で実践した。

  D3. 線の途中の点は「線のウェイポイント」方式を採用。
      connections[i].points = [{x, y}, ...] として線側に持たせる。
      不採用：Blender式に点自体をノードにする案（nodes[] に混ぜる）。
      理由：今のノードは「ヘッダー＋項目＋ソケット」前提のコードなので、
            混ぜると描画・サイドパネル・検証が全部場合分けになる。
      補足：将来 B→A（ウェイポイント→リルートノード）への変換は可能。
            逆（A→B）は分岐を使っていると情報が落ちるので不可逆。
            つまり今の選択は退路が残っている。

  D4. 点の追加・削除の操作は右クリックメニュー方式。
      これに伴い「線をクリックしたら即削除」は廃止した（誤爆防止）。

  D5. フレームの所属は「ドロップ位置で自動判定」。
      ノードの中心座標が入っているフレームに所属する。
      重なっている場合は面積の小さい方（内側）を優先。

  D6. フレームのサイズは「手動リサイズ」。右下の角をドラッグ。
      自動フィットは右クリックメニューの「中身に合わせる」から任意で実行。

  D7. フレームの所属は node.frameId 側にだけ持たせる。
      フレーム側に children を持たせない（二重管理は必ずズレるため）。

  D8. 重なり順は明示的な z-index で管理する。
      フレーム(0) < 線のSVG(1) < ノード(2)
      理由：renderFrames() が毎回 .frame を消して末尾に追加し直すため、
            DOMの順番に依存すると壊れる。全要素 position:absolute なので
            z-index がそのまま効く。

■ 7. データ構造の仕様（現行）
================================================================================

保存されるJSONの全体像：

{
  "version": 1,
  "exportedAt": "2026-09-11T...",     ← エクスポート時のみ付く
  "frames": [
    {
      "id":    "文字列（一意）",
      "label": "フレーム名（空文字可）",
      "x": 40, "y": 40,               ← 左上座標（キャンバス座標）
      "w": 360, "h": 240,             ← 幅・高さ（最小 160 x 120）
      "color": "#5DCAA5"              ← #RRGGBB 形式のみ
    }
  ],
  "nodes": [
    {
      "id":      "文字列（一意）",
      "name":    "ノード名",
      "x": 60, "y": 60,               ← 左上座標。幅は固定180px、高さは内容次第
      "collapsed": false,             ← true でノード名だけ表示
      "frameId": "フレームのid または null",
      "fields": [                     ← 可変個の項目
        {
          "id": "文字列",
          "label": "項目名",
          "value": "本文（改行可）",
          "expanded": true            ← false で折りたたみ
        }
      ]
    }
  ],
  "connections": [
    {
      "id":   "文字列（一意）",
      "from": "出力元ノードのid",
      "to":   "入力先ノードのid",
      "points": [ { "x": 420, "y": 260 } ]   ← 線の折り返し点。空配列可
    }
  ]
}

【互換性の扱い】
  - 旧形式のノード（fields が無く overview を持つ）は読み込み時に
    fields: [{ label: "概要", value: overview }] に変換される。
  - points / frames / frameId が無いJSONを読んでも壊れない（補われる）。
  - 存在しないフレームを指す frameId は null に戻される。
  - 存在しないノードを指す接続は捨てられる。
  - 自己ループ、同じ組み合わせの重複線は捨てられる。
  - ID重複は新しいIDを振り直して解決する。

【座標系】
  points も frames も nodes も、すべて同じ「キャンバス座標」（ズーム前）。
  マウス座標からの変換は toCanvasCoords() を使う（scale で割り戻している）。
  ズーム中に置いた要素が縮小時にズレないのはこのため。

■ 8. 実装済み機能の一覧
================================================================================

【ノード】
  - 「+ 新しいノード」ボタンで追加
  - ドラッグで移動（左ボタンのみ。中ボタン・右ボタンでは動かない）
  - クリックで選択 → 右パネルで名前と項目を編集
  - 項目は可変個。「+ 項目を追加」で追加、✕で削除
  - 項目ごとに折りたたみ（▾／▸）
  - ノード全体の折りたたみ（ヘッダー右の▾／▸）でノード名だけ表示
  - 右パネルの「ノードを削除」で削除（接続も一緒に消える）
  - 入力ソケット（左）・出力ソケット（右）

【接続線】
  - 出力ソケットから入力ソケットへドラッグして接続
  - ベジェ曲線（水平に出て水平に入る形）
  - 線を右クリック → 「ここに点を追加」「この線を削除」
  - 点を右クリック → 「この点を削除」「この線を削除」
  - 点は左ドラッグで移動。何個でも追加可能
  - 当たり判定は透明16px幅のパスで拡張してある

【フレーム】
  - 「+ フレーム」ボタンで追加
  - フレーム内の空いている場所をドラッグ → フレームと中のノードが一緒に動く
  - 右下の角をドラッグでリサイズ
  - ラベルをダブルクリックで名前編集（Enter確定 / Escape取消）
  - 右クリック → 名前を変更 / 中身に合わせる / 色5種 / フレームを削除
  - フレーム削除時、中のノードは消えず所属だけ外れる

【視点操作】
  - ホイールボタン（中ボタン）を押しながら移動 → 視点移動（パン）
  - Ctrl + ホイール → 拡大縮小（0.3倍～2.5倍）

【保存・データ】
  - 自動保存。window.storage があればそれ、なければ localStorage
  - ヘッダー右上のバッジに保存先が出る（「保存先: このブラウザ」等）
  - 「データ」ボタン → JSONの書き出し・読み込みモーダル
    ・書き出し：テキストをコピー / .json ファイルとして保存
      （ファイル名は feature-node-graph-YYYYMMDD-HHmm.json）
    ・読み込み：ファイル選択 または 貼り付け
    ・読み込みモード：置き換え / 今のグラフに追記
  - Artifact上ではダウンロードがサンドボックスでブロックされるため、
    その環境では自動でダウンロードボタンが無効化され、コピーに誘導される

    type:"group"                          →  frames[]
  作業量は小さい（既存のJSON入出力に変換を足すだけ）。
  ※ ユーザーがObsidianを普段使っているかは未確認。使っていないなら価値は薄い。

■ 10. 検証のやり方
================================================================================

R4のとおり、毎回ブラウザを立ち上げての目視確認はしないこと。
代わりに以下の静的チェックを行う。

  (1) JavaScriptの構文チェック
      HTMLから <script> の中身を抜き出し、node --check にかける。
      Pythonでの抜き出し例：

        import re
        s = open('feature-node-graph.html', encoding='utf-8').read()
        m = re.search(r'<script>(.*)</script>', s, re.S)
        open('check.js','w',encoding='utf-8').write(m.group(1))

      そのあと  node --check check.js

  (2) DOMのid整合性チェック
      getElementById('...') で参照しているidが、すべてHTML側に
      定義されているかを突き合わせる。

        used    = set(re.findall(r"getElementById\('([^']+)'\)", s))
        defined = set(re.findall(r'id="([^"]+)"', s))
        print(sorted(used - defined))   # 空ならOK

  (3) grep による確認
      - 削除したはずの古い処理が残っていないか
      - 新しいプロパティが生成箇所すべてに入っているか
        （例: points: は現在4箇所、seedDefault / normalizeGraph /
          attachSockets / applyImport のマージ分）
      - window.storage の直接参照が store レイヤーの中だけに
        収まっているか

  (4) 実際にブラウザで見るのは以下の場合に限る
      - 原因不明のバグの調査
      - 触り心地（当たり判定の太さ、掴みやすさ）の確認
      - レイアウト崩れの確認
